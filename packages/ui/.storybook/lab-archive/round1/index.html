Cross-cutting decisions the exploration surfaced

These came up repeatedly across galleries as agents grounded designs in the real WA source. They're app-wide calls worth settling before Round 2 productionizes anything.

decided → WA-02.04Velocity-zone thresholds — WA owns them, passes to UI

Decision (operator): velocity zones are a derived property of the athlete + lift (they vary by exercise and by the user's individual VBT/LV profile), so WA owns the thresholds and passes resolved zones to the UI as data — the UI stops hardcoding either the titan 1.0/0.75/0.50 or WA 0.75/0.50/0.30 scale. Colors stay in the UI; WA returns numeric bands + zone identity, derived from the per-exercise LV profile when available with per-movement-class defaults otherwise. Values + API shape are a WA research item (in progress) → WA-02.04. Round-2 designs color by injected zones, not constants.

confirmVelocity-loss definition: min/max vs first-to-last

The operator prototype (exercise-detail.html) computes loss as min/max within the set; titan's production VelocityStrip.calculateVelocityLoss and WA's getSetVelocityLossPct both use first-to-last (V1−Vlast)/V1. Galleries followed titan/WA — confirm that's canonical.

buildSession debrief is a composition layer that doesn't exist in WA yet

assembleSessionDebrief, any A–F grade, coach-card generation, and multi-type PR detection are not in workout-analytics — it's a pure analytics lib. The only PR logic is e1RM-only isNewE1RM(current, historyBest). The debrief (and its grade rollup + insight rules) is new composition work, likely in voltras-mcp, on top of computeSessionFatigue + readiness/velocity zones.

noteAuto-regulation function names + fatigue scale

computeAutoRegulation doesn't exist — the real load-suggestion output is computeReadinessAdjustments → ReadinessAdjustments. WA fatigue scores are 0–1 ratios (the 0–100 FatigueIndex is deprecated); junk-volume is the boolean SessionFatigueEstimate.isJunkVolume (velocityRecoveryPct<75 && avgVelLoss>40).

noteNo targetVelocity in WA — target bands are a plan-layer input

WA is explicit that consumers pass their own thresholds. The session-timeline / tempo target bands must be fed from the plan layer, not derived from WA. Decide where the target lives.
